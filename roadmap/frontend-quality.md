## 1. Objetivo de la iniciativa

Establecer una fotografía reproducible de las herramientas y restricciones de calidad del frontend Vue/TypeScript, identificar sus límites y acordar cómo incorporar controles incrementales usando Identity como ejemplo real. FQ-1 solo audita y documenta. No crea gates, baselines, excepciones ni refactorizaciones.

## 2. Estado actual de herramientas

El proyecto declara Yarn 4.10.1 (`packageManager`) con `node-modules` linker. Scripts declarados en `package.json`: `dev`, `build`, `test`, `preview` y `prepare`. `build` encadena `yarn vue-tsc --noEmit && yarn vite build`; `test` ejecuta `vitest run`. No hay scripts de lint, formato, E2E, análisis de dependencias, ciclos, accesibilidad estática, enlaces Markdown ni arquitectura. TypeScript estricto y flags de uso no-unused sí existen, pero solo se ejercitan en el build.

No se encontró `AGENTS.md` en el directorio ni sus dos ancestros revisados. Hay hooks Husky: `pre-commit` solo imprime un mensaje; `commit-msg` ejecuta commitlint mediante `npx --no--`. No lanzan lint, tests, build o typecheck. La única workflow encontrada es `.github/workflows/release.yml`, que se ejecuta en push a `main`, instala con `yarn install --immutable` y publica con semantic-release; no ejecuta gates de calidad antes de release. Esos hooks y workflow no constituyen validación de calidad del código.

TypeScript usa `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch` y `noUncheckedSideEffectImports`. Vite declara plugin Vue y alias; tsconfig y Vite repiten aliases, y `@assets` apunta a `src/helpers` en ambas configuraciones, diferencia de nombre/ruta que conviene revisar en FQ-2. No se encontró configuración Vitest dedicada: el CLI usa defaults y tests seleccionan `happy-dom` con comentarios por archivo. No existen configs ESLint ni Prettier, ni dependencias declaradas para ellos. Impeccable tiene `.impeccable/config.json` leído sin cambios; contiene cuatro valores ignorados/aceptados con razones registradas. No se usó como gate ni se alteró.

## 4. Auditoría de dependencias y límites

`src/modules/` contiene actualmente solo `identity/`. Identity tiene cinco áreas raíz (`auth`, `account`, `users`, `activity`, `shared`) y separa carpetas técnicas dentro de ellas. Es una experiencia concreta de ownership, API/composables/stores/tipos y tests, no una plantilla que se deba imponer a módulos no migrados.

La mayoría del resto del producto permanece en raíces legacy: `views`, `components`, `services`, `stores`, `composables`, `helpers`, `interfaces`, layouts y router. A la fecha de revisión hay 49 archivos `*.test.ts` bajo `src/`, 30 dentro de Identity y 19 fuera; esto cuenta archivos, no calidad ni alcance de cobertura.

Hallazgos de imports observados:

- Identity tiene dependencias internas justificables por composición: Auth consume actividad diaria al completar/restaurar sesión; Users invalida una query de actividad tras mutaciones; Auth lee preferencias de Account; features de Identity comparten `UserRole` y permisos en `shared`. Son contratos/efectos concretos documentados en `identity-structure.md`, no prueba de ciclo por sí solos.
- La integración pública desde el exterior no está formalizada técnicamente. Router, App, main, layouts, componentes, composables legacy, stores legacy y vistas importan rutas profundas de Auth/Users/Account/Activity. Ejemplos de implementación: `@/modules/identity/auth/stores/auth`, `@/modules/identity/users/api/users` y tipos internos. Los consumidores necesitan sesión/rol, listado de usuarios, tipos de usuario y preferencias; parte de ellos atraviesa archivos internos. Esto es el candidato más claro para contratos/fachadas públicas acotadas y reglas de imports graduales, no para restringir de golpe todos los imports existentes.
- Los módulos de negocio propuestos en `frontend-architecture.md` (Catalog, Community, Editorial, Product, Integrations, Insights, Help y App) aún no son directorios raíz de `src/modules/`; el código legacy no está cerrado por dominio. Por ello no se puede afirmar un grafo completo de dependencias entre esos módulos sin primero acordar ownership de las rutas legacy.
- No se ejecutó un grafo automatizado completo. La inspección dirigida no reproduce el antiguo ciclo estático Auth → Axios → Auth: `auth.ts` llama la actividad, el cliente común recibe la sesión con `configureApiAuth()` y no importa Auth. El frontend-architecture e Identity registran que el ciclo histórico no se reproduce en revisiones posteriores. Se informa como “no confirmado en checkout”, no como conteo certificado de cero ciclos, porque no hay detector de ciclos configurado.
- Se detectan dependencias de vistas a componentes de listas bajo `views/list/components` desde Video y vistas de discos; son reutilizaciones legacy entre funcionalidades, con acoplamiento a una carpeta de implementación en lugar de una interfaz de ownership clara. `SidebarMenu` y páginas/gestores de Petitions/Suggestions consumen datos relacionados mediante servicios/stores, potencial duplicación de server state ya documentada en el roadmap arquitectónico.
- La arquitectura de estado es mixta por transición. Pinia mantiene sesión/Auth y estado compartido (incluyendo stores legacy de catálogo, asignaciones, peticiones, soporte y usuarios); TanStack Query 5 sí está instalado y se usa de forma explícita en Users y Activity de Identity. El QueryClient y limpieza de caché privada viven en `src/app/`. El uso de Query no se presume en todo el legado: muchas API y vistas todavía acceden a servicios/Pinia directamente. Query es adecuado para server state con caché/invalidation; Pinia queda para sesión/estado compartido de cliente y flujos ya consolidados. La combinación no debe forzar migración automática ni stores que reflejen el mismo resultado.

La auditoría de Identity advierte consumidores legacy de APIs y tipos de Users, una query de actividad compartida fuera de Activity y la dependencia de preferencias Account/Auth. También registra que `identity/shared` se limita a rol/permisos transversales reales. Esa evidencia favorece una frontera pública mínima y consumible, revisada por módulos, en lugar de “todo lo compartido va a shared”.

## 6. Brechas de cobertura

- No existe job CI de pull request que ejecute test, typecheck o build; el workflow disponible es de release.
- Lint y formato no existen como controles. Tests y build son invocables localmente, no gate de integración.
- No hay suite E2E, cobertura/umbral, detector de ciclos ni prohibiciones de imports profundos.
- No hay contrato técnico de API pública entre features. Identity tiene buenas decisiones registradas, pero el acceso a sus archivos internos sigue permitido por convención.
- No hay accesibilidad automatizada ni verificación continua de Markdown/enlaces.
- No se automatiza el límite de Pinia frente a TanStack Query; no conviene que una regla sustituya la revisión contextual de estado de sesión, server state, caché privada y estado temporal local.

## 8. Estrategia recomendada para código legacy

| Estrategia | Ventaja | Coste/riesgo |
|---|---|---|
| Baseline de infracciones conocidas | Permite exigir reducción y bloquea regresión general desde el día uno. | Requiere herramienta estable y una lista reproducible; no existe hoy y puede congelar ruido o esconder casos si se mantiene mal. |
| Aplicación gradual por módulos | Alinea reglas con ownership conocido; Identity ya tiene mapa y ejemplos de contratos. | Necesita ampliar límites por fases y mantener temporalmente dos niveles de exigencia. |
| Bloquear solo nuevas infracciones | Protege el delta sin convertir deuda histórica en bloqueo inmediato. | Requiere comparar contra base/merge-base y detectar correctamente rutas, renombres y configuración; más complejidad de CI. |
| Reglas globales con excepciones justificadas | Unifica el estándar y hace visibles los desvíos. | Si se activa sobre todo el legado de golpe puede bloquear tareas y producir excepciones permanentes difíciles de gobernar. |

**Recomendación:** empezar por controles sin deuda ambigua (typecheck/tests/build) en CI; definir contratos públicos y ownership para `identity` y módulos nuevos; extender lint/formato y restricciones de imports gradualmente por módulo o archivos nuevos; medir ciclos y accesibilidad para establecer la base antes de bloquear. Para reglas globales, usar inventario versionado solo cuando el detector tenga precisión suficiente y las excepciones tengan propietario y fecha de revisión. No crear esa baseline ni excepciones en FQ-1. Esta mezcla combina adopción por módulos con bloqueo del delta allí donde el tooling soporte comparación fiable; no presupone una baseline ficticia para el frontend actual.

## 9. Riesgos

- Añadir lint/reglas arquitectónicas de golpe puede producir cientos de fallos preexistentes y normalizar una larga lista de ignores.
- Los alias duplicados y SFC requieren que el detector modele el mismo grafo de resolución que Vite/TypeScript; conteos incorrectos invalidarían una baseline.
- Import profundo no significa siempre acoplamiento incorrecto: Router/App deben componer rutas y shell; contratos de Identity se consumen legítimamente desde afuera. Se debe clasificar ownership y API antes de prohibirlos.
- La suite permite pasar aunque un caso muestre DNS en stderr; un gate futuro debe conservar determinismo sin ocultar errores reales.
- Los warnings CSS, Browserslist y bundle podrían volverse más severos con upgrades. Su historia exacta no se determinó y no se tocaron.
- Accesibilidad estática no asegura experiencia accesible; necesita evaluación de teclado/lector/contexto.
- Query y Pinia resuelven estados distintos según ownership y ciclo de vida. Una regla binaria podría empujar datos remotos a Pinia o duplicar cachés.

## 10. Conclusiones de FQ-1

El checkout dispone de dos verificaciones funcionales locales: TypeScript estricto dentro del build y 49 archivos Vitest. Build y suite pasan en la fotografía actual, pero no se ejecutan como checks de CI/PR. Release y hooks no añaden controles de calidad de source. No hay lint, formatter, E2E, análisis de dependencias/ciclos, restricción de imports, a11y automatizada ni comprobador de documentación.

Identity ofrece la referencia más concreta para ownership, tests, API, query y separación de sesión: hay contratos transversales válidos y varias dependencias cruzadas documentadas, pero sus paths internos aún se importan desde fuera. El resto del frontend se mantiene mayoritariamente legacy y no permite aplicar uniformemente una estructura o prohibición de imports todavía. No hay una baseline automatizada fiable para distinguir deuda antigua de nueva. FQ-2 convirtió esta evidencia en criterios propuestos y contratos mínimos; FQ-3 decidirá qué controles introducir y con qué alcance.

## 11. Esqueleto de FQ-2 a FQ-5

- **FQ-2 — Reglas arquitectónicas y arquitectura documental:** definir ownership, dependencias permitidas, API pública, política de shared y criterios de revisión; validar propuestas contra imports reales sin implementar gates. Acordar la organización documental, el índice y las fuentes de verdad antes de mover o dividir documentación.
- **FQ-3 — Automatización incremental:** elegir tooling, comandos, CI y alcance de adopción gradual para typecheck, lint, tests, build, ciclos, imports, accesibilidad estática, formato y enlaces Markdown.
- **FQ-4 — Criterios humanos e instrucciones de agentes:** acordar checklist de PR para decisiones que no se puedan automatizar con fiabilidad: contratos, accesibilidad contextual, estado Pinia/Query/local, deuda/excepciones y revisión visual. Crear o actualizar `AGENTS.md` breve, enlazando las convenciones y documentación definitiva acordadas en FQ-2.
- **FQ-5 — Adopción y seguimiento:** aplicar los controles aprobados, revisar resultados de CI, registrar deuda nueva frente a preexistente y ajustar fases con evidencia.
- **FQ-6 — Migración documental:** ejecutar la extracción, conciliación y archivo gradual descritos por FQ-2. Mantenerla como fase propia si excede las referencias mínimas necesarias para FQ-4; no declarar cerrada la iniciativa FQ hasta completar o replanificar esta fase.

FQ-1 y FQ-2 no ejecutan FQ-3 a FQ-6.

## 13. Resultado de FQ-2 — criterios arquitectónicos propuestos

FQ-2 toma como base el checkout y el análisis de FQ-1, no declaraciones históricas sin fecha. Los criterios de esta sección quedan acordados como dirección de diseño para cambios futuros; no se implementan ni se convierten todavía en un manual técnico canónico. Las decisiones suficientemente concretas son: ownership por funcionalidad, dependencias dirigidas, una entrada pública pequeña por funcionalidad, reglas diferenciadas para piezas de presentación/datos, documentación canónica bajo `docs/frontend/` y fases separadas para automatización, agentes y migración documental.

### 13.1 Principios de organización

1. Organizar primero por funcionalidad y ownership. Dentro de una funcionalidad se agrupa el código técnico necesario; no crear una carpeta por cada tipo de archivo si no hay volumen o motivo real.
2. Cada vista, componente, composable, API y tipo tiene un propietario claro. El lugar donde se renderiza no determina automáticamente quién posee su contrato o dato.
3. Mantener dependencias dirigidas: presentación puede coordinar comportamiento y consultar APIs/composables; capas de datos no importan vistas/componentes; funcionalidades no dependen de la implementación interna de otra.
4. Compartir una pieza cuando haya consumidores reales con semántica común y responsable común. Reutilizar UI genérica no transfiere propiedad del dato de negocio.
5. Mantener los ciclos fuera del diseño. La coordinación entre capas se hace mediante contratos de bajo nivel, callbacks/eventos o composición en App, no mediante import circular.
6. Introducir solo capas que contengan responsabilidad, contrato, política o prueba propia. No imponer DDD completo, arquitectura hexagonal, interfaces especulativas, composables por vista o simetría entre módulos.
7. La estructura de `identity/` demuestra una asignación útil (auth/account/users/activity/shared); no es requisito de carpetas para Catalog, Editorial u otros módulos. Repetir solo las decisiones que resuelvan necesidades observadas.

### 13.2 Responsabilidades por pieza

| Pieza | Responsabilidad y dependencias esperadas | Excepción legítima / señal para revisión |
|---|---|---|
| **View** | Componer una pantalla, derivar estado de presentación, conectar navegación y coordinar interacciones del flujo. Puede consumir componentes, composables, contratos públicos, Pinia/Query según ownership y estado local. | Es legítimo que una vista orqueste un caso de uso con varias fuentes. Revisar si acumula reglas de negocio reutilizadas o política de transporte; no medir por líneas. |
| **Component** | Presentar UI e interacciones locales, emitir intención/datos hacia su owner. Mantener props/emits y estado temporal visual. | Un componente de feature puede conocer su contrato de dominio; no convertirlo en biblioteca genérica por tener dos consumidores parecidos. La extracción transversal requiere semántica y owner compartidos. |
| **Composable** | Encapsular comportamiento reactivo cohesionado que se reutiliza, es complejo de probar fuera de la vista o posee ciclo de vida/watchers coordinados. | Una operación corta de una sola vista puede quedarse en esa vista. No extraer por convención, tamaño o “un composable por vista”. |
| **API** | Hablar con transporte HTTP, serializar parámetros y adaptar/validar la respuesta contra el contrato remoto; aceptar señales de cancelación donde la consulta pueda cancelarse. | Un API pequeño puede ser función directa dentro del owner sin carpeta/capa extra. La API no presenta UI ni mantiene estado de vista. |
| **Pinia** | Estado cliente compartido con ciclo de vida explícito: sesión/Auth, preferencias persistidas o estado transversal que varios consumidores modifican/observan. | Store legacy puede mantenerse mientras se migra. No duplicar resultados de Query en Pinia ni globalizar filtros/modales efímeros. |
| **TanStack Query** | Estado remoto cacheable: query keys identifican filtros/identidad; API recibe signal; mutations invalidan datos relacionados; datos privados se aíslan y limpian en cambios de sesión/permiso. | No toda llamada HTTP necesita Query. Una acción puntual o dato no compartido puede seguir una función API simple; decisiones basadas en UX/frecuencia/consistencia. |
| **Utils** | Transformaciones puras, deterministas y sin estado reactivo, transporte o side effects; nombradas por regla compartida real. | Una función local pequeña se queda junto a su owner. `shared` no es cajón de sastre. |
| **Types** | Tipos del payload/respuesta y conceptos de dominio pertenecen a la funcionalidad que los define; tipos solo de UI viven cerca de su UI. | Tipo transversal se expone por contrato público o área compartida con consumers probados. Evitar copiar DTOs en consumidores y evitar tipos genéricos que pierdan semántica. |

Una excepción es legítima si la relación forma parte de composición de aplicación (Router/App/bootstrap), si un módulo consume expresamente un contrato publicado, o si hay un acoplamiento transitorio heredado con propietario, motivo y ruta de migración. Su justificación se documenta donde se defina la regla técnica; no se añade una excepción automática en esta fase.

### 13.3 Contratos públicos entre funcionalidades

Un contrato público es el conjunto pequeño y deliberado de símbolos que otra funcionalidad necesita para usar una capacidad sin conocer sus carpetas internas: funciones de caso de uso/API, composables consumibles, tipos estables y, cuando el ciclo de vida lo requiera, una interfaz de estado de cliente. No es “todo lo exportado”, ni todos los archivos actuales, ni una API de red distinta.

**Forma objetivo:** cada módulo maduro expone una entrada explícita por área/capacidad, por ejemplo `src/modules/identity/auth/public.ts`, `users/public.ts`, `account/public.ts` y `activity/public.ts` (o subpath `index.ts` con la misma intención). Los nombres son propuesta de destino; no se crean aquí. Cada entrada exporta símbolos enumerados y mantiene imports internos del módulo fuera de ella. No crear un barrel raíz que reexporte toda la implementación ni una fachada que solo delegue un método sin aportar estabilidad/ownership.

**Privado por defecto:** rutas a `/api/`, `/stores/`, `/composables/`, `/types/`, vistas/componentes y helpers internos bajo la funcionalidad son privadas para consumidores externos, salvo símbolos explícitamente exportados por su entrada pública. Los imports relativos entre archivos de una misma funcionalidad son normales. No se pretende bloquear cada ruta profunda de inmediato mientras existan consumidores legacy.

Contratos mínimos concretos sugeridos a partir de los consumidores actuales:

| Capacidad | Consumidor real / necesidad | Superficie pública mínima a evaluar en implementación |
|---|---|---|
| Auth y roles | `router/index.ts`, `App.vue`, `main.ts`, Sidebar, componentes y vistas consultan estado/capacidades de sesión; Router usa `UserRole`, `hasMinimumRole`, `useAuthStore` y Login. | `UserRole`/contratos de autorización, `hasMinimumRole`, acceso al estado/capacidad Auth estable y `LoginView`. Mantener transport (`sessionAuth`), coordinador de pestañas y tipos privados salvo bootstrap que requiera composición explícita. Router y shell son composition roots y pueden usar API pública; `main.ts` conserva una excepción de bootstrap documentada si debe conectar Axios/callbacks. |
| Users | Vistas legacy consumen `getRvUsers`, `getSuperusers`, `getGlobalActivity` y tipos `RvUser`, `Superuser`, además de APIs administrativas internas. `Activity` consume `getGlobalActivity`. | Exponer solo las consultas/tipos realmente consumidos por otros owners. Mutaciones y query keys de User Management no se publican sin un segundo consumidor funcional. Separar el contrato de listado común de acciones administrativas si su ownership/permiso difiere. |
| Account preferences | Sidebar y `useDashboardConfig` leen preferencias; Auth aplica preferencias de perfil durante sesión. | Contrato de lectura/actualización de preferencias de cuenta y el tipo de configuración necesario; evitar exponer el store completo como API si un composable estable basta. Auth→Account queda como dependencia explícita por integración de sesión/perfil. |
| Activity | `Users` invalida `activityDashboardQueryKey`; composables de Activity consultan Auth y la actividad legacy obtiene `getGlobalActivity` de Users. | Si Users debe invalidar el dashboard, publicar una operación/key de invalidación estable (o un evento de dominio) para no importar un composable entero. Mantener API/Query de Activity privada a Activity en otros casos. Resolver en implementación si global activity es propiedad de Users o Activity. |
| Shared identidad | Auth, Users, Activity, Router, Sidebar y vistas usan `UserRole` y permisos. | Publicar solo `UserRole` y función de comparación de permisos compartidos. `shared` exige al menos dos owners actuales y semántica única; no mover DTOs o servicios por conveniencia. |

Las propuestas no mueven ownership actual ni resuelven automáticamente el contrato de actividad global. La adopción será por consumidor: introducir entrada pública para un caso, migrar callers observados, verificar búsqueda de referencias, luego declarar el path interno privado para esa zona. Consumers de tests pueden importar internals deliberadamente para probar implementación; la regla de imports debe distinguir producción de tests.

### 13.4 Matriz de dependencias

“Permitida” expresa dirección o composición con contrato; “restringida” implica que el diseño no debe introducirla; “pendiente” requiere precisar el owner o contrato antes de bloquear. No se afirma un grafo completo para dominios que solo existen hoy como código legacy.

| Origen | Destino | Estado/dirección acordada | Comprobable / revisión |
|---|---|---|---|
| Funcionalidad | API, componentes, composables, tipos y estado propios | Permitida dentro del owner según responsabilidades. | Parcialmente automática por capas; ownership de cada archivo requiere clasificación inicial. |
| Funcionalidad A | API pública de funcionalidad B | Permitida si el contrato es necesario y el sentido de dependencia no crea ciclo. | Automática tras definir entradas; revisión humana para justificar necesidad y ownership. |
| Funcionalidad A | Ruta interna de B (vista/API/store/composable/tipo no publicado) | Restringida como patrón futuro; legacy existente se migra por etapas. | Sí en módulos adoptados una vez enumerado el API público; falsos positivos en tests y composition roots. |
| Identity/Auth | Identity/Account preferences | Permitida y documentada: Auth aplica configuración recibida durante sesión. | Automatizar dirección módulo→módulo; revisión para evitar que Account adquiera ownership de sesión. |
| Identity/Auth | Identity/Activity daily notification | Permitida de forma acotada: Auth notifica evento tras login/restauración. | El edge puede detectarse; revisión decide si se mantiene como caso de uso o evento. No convertirlo en dependencia de estadísticas. |
| Identity/Users | Identity/Activity query key/dashboard invalidation | Permitida por contrato; la importación actual de composable completo es candidata a API más pequeña. | Ciclo/import detectables; elección entre invalidation API/evento requiere revisión. |
| Identity/Activity | Identity/Users API `getGlobalActivity` | Dependencia actual pero ownership pendiente; no bloquear hasta decidir si endpoint/consulta se mueve o se expone. | Import detectable; el ownership necesita validar dominio y consumidores. |
| Identity/* | Identity/Shared roles/permisos | Permitida solo para conceptos realmente transversales dentro de Identity; `shared` no depende de features concretas. | Regla de dirección automatizable; decidir nuevos candidatos es humano. |
| Identity | `src/services/api` legacy | Excepción transitoria observada para notificación diaria/infraestructura Axios. No sumar dependencias de negocio legacy nuevas sin contrato. | Detector puede reportar; whitelist temporal exigiría decisión posterior y propietario/fecha, aún no existe. |
| Código legacy (views/components/stores/composables) | API pública Identity | Permitida durante convivencia y migración. | Automática con paths públicos; inventariar imports existentes. |
| Código legacy | Internos Identity | Se tolera temporalmente como deuda conocida; prohibir nuevas referencias en zonas adoptadas al existir surface pública. | Solo automatizable con baseline/delta y mapa de paths; sin baseline no bloquear globalmente. |
| Identity | vistas/componentes/stores/composables legacy | Restringida: Identity no debe depender de UI/estado legacy. La infraestructura HTTP compartida es excepción indicada arriba. | Imports detectables; clasificación de import por responsabilidad requiere revisión. |
| Router | vistas de ruta, meta de autorización, contrato público de Auth | Permitida; es composition root de navegación. Mantener lazy loading salvo excepción deliberada. | Automático para ubicación/import y lint de capas; rutas/permisos requieren pruebas/revisión. |
| Router | API HTTP, stores de negocio no necesarios para navegación, UI interna de módulos | Restringida. Guard consulta sesión/capacidad; no orquesta CRUD de features. | Regla de imports; revisión de política de autorización. |
| App / layouts shell | Router, Auth público, stores/query de shell, UI de shell y configuración global | Permitida para componer lifecycle/shell. | Mapa de capas automatizable; decisión de ownership de cada estado revisable. |
| App / bootstrap | detalles de transporte/coordinación necesarios para cablear integraciones | Permitida como excepción de composición en `main.ts`; no extender al resto de la app. | Import detectable, allowlist pequeña y documentada; revisión humana obligatoria. |
| Módulos de negocio entre sí | API pública en una dirección acíclica | Permitida si el flujo de negocio requiere la capacidad; dependencias de vuelta deben resolverse en composition root/contrato. | Grafo/ciclos sí; legitimidad del edge y dirección objetivo, revisión. |
| `shared` | módulos de negocio o implementación concreta | Restringida; shared no importa owners ni se convierte en cajón de sastre. | Regla de imports automatizable. |
| Components | vistas / Router / APIs / stores globales | En general restringida; componente recibe contrato/props/emits y delega intención. Componentes de dominio pueden usar composables públicos si eso evita duplicar comportamiento. | Imports detectables; “componente de dominio” y uso de estado local requieren juicio. |
| Composables | API, Query, estado público del owner y utils | Permitida según comportamiento que encapsulan. | Import graph automatizable parcialmente; side effects y cohesión requieren revisión. |
| API | cliente de transporte y tipos de contrato | Permitida. | Regla de capas; validar contrato y efectos requiere tests/revisión. |
| API | vistas/componentes/Router/QueryClient | Restringida. API no controla presentación ni caché global. | Fácil de automatizar por path con precisión razonable. |
| Pinia store | API/contratos de su owner y dependencias explícitas de sesión | Permitida cuando corresponde; evitar que una store de negocio importe otra store para copiar datos. | Imports/ciclos automatizables; server state duplicado necesita revisión. |
| Query composable | API, query keys y auth público para sesión/permiso | Permitida. Query composable posee política de cache key, `signal`, habilitación y stale-session. | Checks parciales; verificar contenido de key/invalidation semánticamente requiere revisión/tests. |
| Query data | Pinia como espejo persistente | Restringida salvo requisito explícito de cliente con owner/ciclo de vida distintos. | Detección heurística, principalmente revisión. |

Las direcciones se refieren a dependencias de módulos, no a la jerarquía visual de carpetas. La integración Auth→notificación de Activity es intención de aplicación reconocida; el antiguo ciclo Auth/Axios no está demostrado por el checkout actual, pero ciclo cero debe confirmarse con herramienta futura.

No crear directorios ni archivos vacíos por anticipación. FQ-2 debe elegir una estructura concreta luego de validar audiencia y propiedad. Una forma objetivo compacta, si se aprueba, sería:

Los ADR registran contexto, decisión, alternativas relevantes, consecuencias, estado y referencias; una decisión reemplazada apunta a su sucesora en vez de reescribirse silenciosamente.

### Criterios para crear, dividir o archivar

- Crear documento cuando haya un propietario identificable, una audiencia recurrente y contenido que no tenga una fuente canónica adecuada. Evitar páginas cuyo único contenido sea una lista de enlaces o una copia de otro archivo.
- Dividir cuando haya responsabilidades y ciclos de cambio distintos, al menos una fuente estable pueda expresarse sin la cronología, y cada nuevo documento tenga propósito, propietario/ámbito y enlace entrante. El tamaño por sí solo no obliga a dividir.
- Mantener una página de módulo cuando haya contratos y dependencias propios que cambien independientemente; no crear una para cada vista o carpeta técnica.
- Registrar decisiones arquitectónicas relevantes en ADR; dejar en roadmap la propuesta temporal, subtareas, progreso y cierre. Un roadmap puede citar la decisión pero no ser su única copia permanente.
- Archivar un plan cerrado marcando su estado y fecha, conservando referencias entrantes, evitando que aparezca como tarea activa en el índice. El contenido puramente histórico puede quedar en su roadmap o changelog según si documenta una iniciativa o una release.
- No borrar ni renombrar durante una migración documental sin actualizar enlaces entrantes conocidos. Cuando haya consumidores externos o referencias históricas difíciles de enumerar, conservar una nota corta en la ruta antigua que enlace la fuente nueva.
- Marcar afirmaciones volátiles con fecha/fase y distinguir “estado al cierre” de “estado actual”. Los comandos/configuración operativos deben tener dueño y verificarse contra el checkout antes de presentarse como vigentes.

`AGENTS.md` debe limitarse a instrucciones accionables y estables para agentes: alcance de edición, comandos comprobados, límites de seguridad/servicios y enlaces a la arquitectura, convenciones y módulo pertinente. Conviene mantenerlo breve para que el agente no reciba múltiples copias que compitan.

Las explicaciones extensas de ownership, contratos, dependencias, decisiones, procedimientos y cronología pertenecen a páginas técnicas, ADRs o roadmaps. Las instrucciones que cambian por módulo pueden estar en un `AGENTS.md` local solo si hay una necesidad real y con alcance claro. `CLAUDE.md` no debe ser la única fuente de verdad de reglas comunes; la futura FQ-4 debe resolver compatibilidad de instrucciones de agentes y enlaces sin copiar manuales enteros.
